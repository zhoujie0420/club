# HOLE CLUB UI 产品需求文档（重构版）

> 文档版本：V1.0  
> 产品阶段：可交互 MVP → 可试营业版本  
> 适用终端：员工移动端 H5 / 微信小程序（主端），顾客会员端（后续独立）  
> 基于项目：UniApp + Vue 3 + TypeScript；Go API 骨架  
> 更新日期：2026-09-13

## 1. 文档目的

本 PRD 用于统一 HOLE CLUB 订台系统的产品定位、信息架构、业务流程、页面状态与视觉规范，作为产品、UI、前端、后端及门店运营的共同验收依据。

当前代码已覆盖“工作台 → 台位 → 创建预订 → 订单操作 → 会员展示”的基本演示链路，但员工端和顾客端混用、浅色与深色视觉并存、状态口径不统一。重构后优先交付一套适合门店现场使用的员工运营端；会员端作为独立产品入口规划，避免角色和导航冲突。

## 2. 产品定义

### 2.1 产品定位

HOLE CLUB 是面向夜店门店员工的移动端台位与订单协作工具，帮助销售、前台、服务员和店长在高噪声、弱光、快节奏的营业环境中，快速完成订台、到店、开台、加单、结账和清台。

核心价值不是“展示夜店氛围”，而是让现场人员在 3 次点击内找到目标台位或订单，并清楚知道下一步该做什么。

### 2.2 目标用户

| 角色 | 核心任务 | 默认首页 | 数据范围 |
| --- | --- | --- | --- |
| 销售 | 创建预订、跟进客户、查看本人业绩 | 工作台 | 本人订单为主 |
| 前台 | 核验预订、确认到店、分配或调整台位 | 台位 | 当日全场订单 |
| 服务员 | 开台、加单、发起结账、清台 | 台位 | 负责区域 / 全场台位 |
| 店长 / 老板 | 查看经营概览、异常订单、销售排行 | 工作台 | 门店全部数据 |

### 2.3 产品目标

- 员工可在 60 秒内完成一笔标准订台。
- 到店、开台、加单、结账、清台等高频操作单手可完成。
- 台位状态与订单状态保持一一对应，页面间不出现冲突。
- 关键金额、客户手机号、取消和结账操作具备权限控制与二次确认。
- 视觉在弱光环境下仍有足够对比度，状态不只依赖颜色辨识。

### 2.4 非目标

V1 不包含库存管理、酒水采购、排班、复杂 CRM、线上支付通道、发票、跨门店经营分析和完整会员积分结算。可保留入口占位，但不可进入半成品流程。

## 3. 当前版本问题与重构原则

| 当前问题 | 影响 | 重构要求 |
| --- | --- | --- |
| 工作台 / 台位 / 订单为浅色，会员页为深色 | 品牌割裂，页面像两个产品 | 员工端统一深色运营主题；顾客端独立主题与入口 |
| 员工工作台出现“客户、我的”，会员页又使用顾客导航 | 角色认知混乱 | 员工端与顾客端不共用底部导航 |
| 订台步骤显示两步，但全部内容在一页完成 | 进度反馈失真 | 改为真实两步流程，或删除步骤条；本 PRD 采用两步流程 |
| 台位总数显示 32，但页面实际仅构造 18 个台位 | 统计不可信 | 台位图和统计只读取同一台位配置 / API |
| 订单结账只改变状态，未保存支付方式 | 财务数据失真 | 结账必须保存支付方式、实收金额、操作人和时间 |
| localStorage 演示数据日期固定 | 跨日后“今日”统计错误 | 所有今日数据按门店营业日动态计算 |
| 缺少加载、失败、断网、冲突状态 | 真实营业环境不可用 | 每个核心页面必须覆盖完整系统状态 |

重构原则：先保证现场效率和数据可信，再表达品牌氛围；先完成单门店闭环，再扩展会员与营销。

1. **工作台**：经营概览、待办、快捷操作。

## 6. 核心业务规则

### 6.1 营业日

- “今日”按门店配置的营业日起止时间计算，默认当日 18:00 至次日 06:00，不按自然日 00:00 切分。
- 所有页面顶部需展示当前营业日；跨日后重新进入页面自动刷新。

### 6.2 订单状态机

```text
待到店 ──确认到店──> 已到店 ──开台──> 消费中 ──结账成功──> 待清台 ──清台完成──> 已完成
   └────────取消预订────────> 已取消
```

- 已取消、已完成为终态，普通角色不可逆转。
- “确认到店”和“开台”可连续操作，但必须保留两个时间点。
- 结账失败不得改变订单状态。
- 空闲台位创建预订后变为“已预订”；完成清台后恢复“空闲”。

### 6.3 台位状态

| 状态 | 触发条件 | 可执行操作 |
| --- | --- | --- |
| 空闲 | 无有效订单 | 创建预订、现场开台 |
| 已预订 | 关联待到店订单 | 查看订单、确认到店、取消 |
| 已到店 | 客户已核验 | 开台、改台 |
| 消费中 | 已开台 | 加单、查看账单、结账 |
| 待清台 | 已结账 | 完成清台 |
| 停用 | 维修或不开放 | 查看原因；店长可恢复 |

### 6.4 金额规则

- 列表展示“应收金额”；结账页同时展示原价、优惠、应收、实收。
- 金额统一使用人民币符号和千分位，例如 `¥3,880`。
- 加单行金额 = 单价 × 数量；订单金额由明细实时汇总，前端不得写死。

## 7. 核心任务流程

### 7.1 创建预订

工作台 / 空闲台位 → 客户与时间 → 校验手机号和人数 → 选择可用台位 → 选择套餐 → 核对摘要 → 创建成功 → 订单详情。

冲突规则：提交前服务端再次校验台位；如已被他人占用，保留用户已填信息，返回台位选择并标出“刚刚被占用”。

### 7.2 到店至清台

搜索订单或点击台位 → 核对客户 → 确认到店 → 开台 → 加单 → 核对账单 → 选择支付方式 → 结账 → 待清台 → 完成清台。

### 7.3 快速查找

- 台位页：按区域与状态筛选，点击台位查看摘要。
- 订单页：支持客户姓名、完整 / 尾号手机号、台号、订单号搜索。
- 搜索结果关键词高亮；无结果时保留搜索词并提供“清空条件”。

## 8. 页面级 UI 需求

### E01 工作台

**目标**：10 秒内看到当前营业状况和最紧急待办。

**页面结构**：

1. 顶部：问候语、员工姓名、角色标签、营业日；点击头像进入“我的”。
2. 营业状态条：营业中 / 未营业 / 即将打烊，附预计高峰时间。
3. 核心指标：今日订台、待到店、消费中、今日实收。默认两列卡片。
4. 快捷操作：创建预订、实时台位、订单管理。
5. 今日待办：按紧急程度排列“已超时未到店、即将到店、待清台”。
6. 最近动态：最多 5 条，点击进入订单详情。
7. 店长专属：销售排行与异常订单，只对店长 / 老板显示。

**交互要求**：

- 指标卡点击后进入带对应筛选条件的订单页。
- 下拉刷新全部数据；显示“更新于 HH:mm:ss”。
- 指标为 0 时仍展示卡片，不使用 `--`；请求失败才使用 `--`。
- 无待办时显示“当前没有紧急待办”，不隐藏整个区域。

### E02 实时台位

**目标**：快速定位某个台位及全场占用情况。

**页面结构**：

1. 顶部统计：全部、空闲、已预订、使用中、待清台。
2. 筛选栏：状态筛选、区域筛选；筛选栏滚动吸顶。
3. 平面图：舞台、DJ 台、舞池、吧台作为空间锚点；台位按真实配置定位。
4. 图例：颜色 + 图形 / 文案双编码，始终可见。
5. 更新时间与刷新按钮。

**台位卡内容**：台号、状态；空间允许时显示人数或客户姓氏。热区不小于 44 × 44 px。

**交互要求**：

- 点击台位打开 E03，不直接跳页。
- 平面图支持双指缩放和拖动；提供“复位”按钮。
- 发生状态更新时以 300 ms 轻动效过渡，不闪屏。
- 台位配置、统计数字和订单必须来自同一数据源。

### E03 台位详情抽屉

**空闲状态**：台号、区域、建议人数、最低消费、创建预订、现场开台。

**占用状态**：订单状态、客户、到店时间、人数、归属销售、当前金额、主操作按钮、查看订单。

主操作按钮必须根据状态唯一突出：

- 已预订 → “确认到店”
- 已到店 → “开台”
- 消费中 → “查看账单 / 加单”
- 待清台 → “完成清台”

### E04 创建预订－客户与时间

**字段顺序**：到店日期、到店时间、人数、客户手机号、客户姓名、微信号、客户备注。

**规则**：

- 手机号必填并按中国大陆 11 位格式校验；若用于海外号码，后续增加国家码选择。
- 输入完整手机号后匹配已有客户，展示脱敏历史信息，由员工确认带入。
- 人数范围 1–99，默认 6；不使用自由文本表达人数。
- 时间选择以 30 分钟为步长；过去时间不可选。
- 点击“下一步”时进行行内校验，首个错误字段自动滚入视野。

### E05 创建预订－台位与套餐

**页面结构**：

1. 顶部展示第一步摘要，可返回修改。
2. 展示满足人数、时间和区域条件的可用台位；默认推荐容量最接近的台位。
3. 套餐卡展示名称、内容、原价 / 活动价、适用人数和库存状态。
4. 底部固定栏展示台位、套餐、应收金额和“确认预订”。

**提交反馈**：按钮进入加载态且防重复点击。成功后进入订单详情并显示成功提示；失败时保留表单内容。

### E06 订单列表

**页面结构**：

1. 搜索框。
2. 状态标签：全部、待到店、进行中、已完成、已取消；显示数量。
3. 日期筛选默认“本营业日”，可切换昨天 / 近 7 日 / 自定义。
4. 订单卡：台号、客户、人数、到店时间、销售、套餐摘要、金额、状态。
5. 右下角创建按钮；有底部导航时，按钮底边距需避开安全区。

**排序**：待到店按到店时间升序；进行中按最近操作时间降序；已完成按结账时间降序。

**异常提示**：超过预计到店时间 30 分钟仍未到店，卡片显示“已超时”警示，但订单状态仍为“待到店”。

### E07 订单详情

采用独立页面，不使用内容高度不稳定的半屏抽屉，以承载完整生命周期。

**页面结构**：

1. 状态头：当前状态、台号、主操作。
2. 客户信息：姓名、脱敏手机号、人数、到店时间、备注。
3. 消费明细：商品、数量、单价、小计；消费中可进入加单。
4. 费用汇总：原价、优惠、应收、实收。
5. 订单信息：订单号、销售、创建人、创建时间。
6. 操作记录：到店、开台、加单、结账、清台的时间与操作人。
7. 底部操作栏：一个主操作 + 最多两个次操作；危险操作进入“更多”。

**隐私**：手机号默认脱敏；具备权限的角色点击“查看”后记录审计日志。

### E08 加单

- 顶部搜索商品，分类吸顶；商品卡展示名称、单价、库存状态。
- 已选商品在底部购物栏汇总数量和金额。
- 支持增减数量、整行删除、订单备注。
- 缺货商品不可点击并显示“已售罄”。
- 提交前展示本次新增金额；成功后回到订单详情并定位到新增项。

### E09 结账确认

- 展示完整账单、优惠和应收金额。
- 支付方式：微信、支付宝、现金；V1 记录线下收款，不唤起真实支付。
- 实收金额默认等于应收，可由有权限角色修改。
- 点击“确认已收款”弹出二次确认，文案包含台号与实收金额。
- 成功后状态变为“待清台”，保存支付方式、实收、操作人、时间。

### E10 我的

展示头像、姓名、角色、所属门店、当前班次、版本号；提供切换演示角色、通知设置、隐私说明、退出登录。生产环境的角色由账号权限决定，不允许自由切换。

### C02 顾客会员中心（P2）

会员中心迁移至独立顾客端，不再从员工端订单页直接进入。保留现有“黑金 / 酸性绿”品牌方向，但积分、等级、权益必须读取真实会员账户；没有数据时不展示伪造会员号和进度。

## 9. 全局状态与反馈

每个数据页面必须设计以下状态：

| 状态 | UI 表现 | 用户操作 |
| --- | --- | --- |
| 首次加载 | 骨架屏，结构与真实内容一致 | 无需操作 |
| 局部刷新 | 保留旧数据，显示轻量刷新标记 | 可继续浏览 |
| 空数据 | 图标 + 原因 + 建议动作 | 创建预订 / 清空筛选 |
| 搜索无结果 | 展示搜索词和筛选条件 | 清空条件 |
| 网络失败 | 错误摘要，不暴露技术栈 | 重试 |
| 弱网 / 离线 | 顶部常驻横条，禁止高风险提交 | 恢复网络后重试 |
| 并发冲突 | 明确指出已变化的台位 / 订单 | 刷新并重新选择 |
| 提交中 | 按钮 loading，禁止重复提交 | 等待结果 |
| 成功 | Toast + 页面数据立即更新 | 继续后续任务 |
| 无权限 | 说明所需角色 | 返回或联系店长 |

Toast 只用于无需用户决策的轻提示；取消、结账、反结账等操作必须使用确认对话框。

## 10. 视觉设计系统

### 10.1 设计关键词

**专业、迅速、夜场感、低眩光、高识别。** 员工端不采用大面积纯黑或高饱和霓虹，避免长时间使用疲劳；品牌酸性绿仅用于主操作和焦点。

### 10.2 色彩 Token

| Token | 色值 | 用途 |
| --- | --- | --- |
| `bg/base` | `#0D0D12` | 页面背景 |
| `bg/surface` | `#17171E` | 卡片 / 导航 |
| `bg/elevated` | `#202028` | 抽屉 / 弹层 |
| `border/default` | `#2B2B34` | 分割与边框 |
| `text/primary` | `#F5F3ED` | 主文本 |
| `text/secondary` | `#A2A2AD` | 辅助文本 |
| `text/tertiary` | `#6F6F7A` | 弱提示 |
| `brand/primary` | `#D7FF3F` | 主按钮、选中、焦点 |
| `status/free` | `#35D07F` | 空闲 / 成功 |
| `status/reserved` | `#FFB547` | 已预订 / 提醒 |
| `status/serving` | `#5B9CFF` | 已到店 / 消费中 |
| `status/cleaning` | `#A3A3AD` | 待清台 |
| `status/danger` | `#FF6262` | 取消 / 超时 / 错误 |

正文与背景对比度不低于 WCAG AA。状态必须同时展示文字或图标，不允许仅靠颜色区分。

### 10.3 字体与字号

- 中文：系统字体 `PingFang SC`；数字：`Inter` 或系统无衬线字体。
- 页面标题 24 px / 700；区块标题 17 px / 700；正文 14 px / 400；辅助信息 12 px / 400；最低可读字号 11 px。
- 金额与关键数字使用等宽数字特性；不要通过过度加粗制造层级。

### 10.4 间距、圆角和阴影

- 基础间距单位 4 px；常用间距 8 / 12 / 16 / 24 / 32 px。
- 页面左右边距 16 px；卡片内边距 16 px；列表项最小高度 56 px。
- 小组件圆角 8 px；卡片 12 px；底部抽屉顶部 20 px。
- 深色界面主要用层级色和边框区分，不依赖重阴影。

### 10.5 组件规范

- 主按钮：高度 48 px，品牌绿底、深色文字；同屏最多一个。
- 次按钮：高度 44–48 px，深色表面 + 1 px 边框。
- 危险按钮：红色文字 / 描边，最终确认弹窗使用红色主操作。
- 输入框：可点击区域至少 48 px，标签常驻，错误文案位于字段下方。
- 状态标签：高度 24 px，包含状态文字；颜色使用 10%–16% 透明背景。
- 底部导航：高度 56 px + 安全区；图标 22 px，标签 11 px。
- 所有图标使用同一套线性图标，不再使用 `⌂`、`▦`、`≡` 等文本符号代替。

## 11. 动效与触觉反馈

- 页面切换 200–250 ms；底部抽屉 240 ms；状态变化 180–300 ms。
- 动效服务于状态理解，不使用循环闪烁和大范围霓虹动画。
- 创建成功、结账成功可使用一次轻触觉反馈；错误使用一次明显反馈。
- 尊重系统“减少动态效果”设置。

## 12. 多端与适配

- 设计基准宽度 375 px，覆盖 320–480 px；内容最大宽度 480 px。
- 顶部和底部必须适配安全区、微信小程序胶囊和键盘顶起。
- 键盘出现时，当前输入字段及错误提示不可被遮挡。
- H5 桌面浏览时居中显示移动端画布；不在 V1 单独设计后台桌面版。
- 台位图根据容器缩放，但台位点击热区不得小于 44 px。

## 14. 数据与接口要求

前端不得继续以 localStorage 作为生产数据源。P0 至少需要：

- 登录 / 当前员工与权限
- 营业日概览与待办
- 台位配置、台位实时状态、状态更新时间
- 订单列表、订单详情、创建订单
- 订单状态流转（带版本号或幂等键）
- 商品 / 套餐列表、加单
- 结账记录
- 操作日志

所有写操作需要返回最新订单和台位状态。客户端提交需携带唯一请求 ID，避免弱网重试产生重复订单或重复加单。

## 16. UI 验收标准

### 16.1 功能验收

- 从创建预订到订单详情形成完整闭环，订单与台位状态同步。
- 每一种订单状态只出现允许的操作，终态不可被普通角色修改。
- 列表、详情、工作台的金额与数量口径一致。
- 台位冲突、重复点击、断网和服务端失败均不会产生重复数据。
- 搜索支持客户、手机号、台号和订单号，筛选结果与数量一致。

### 16.2 UI 验收

- 所有员工端页面使用统一 Token，无浅色 / 深色主题跳变。
- 320–480 px 宽度无横向溢出，安全区和键盘场景无遮挡。
- 按钮热区不小于 44 × 44 px，正文不小于 12 px（极少量标签最低 11 px）。
- 加载、空、失败、无权限、冲突、提交中状态齐全。
- 状态识别同时具备颜色和文字 / 图标。
- 使用真实图标资产，不出现字符图标风格不一致。

### 16.3 性能验收

- 首屏可操作时间目标 ≤ 2.5 秒（常规 4G / Wi-Fi）。
- 常规页面切换反馈 ≤ 300 ms；写操作点击后 100 ms 内出现反馈。
- 台位状态正常营业时刷新延迟目标 ≤ 5 秒。

## 17. 交付物清单

## 18. 建议实施顺序

1. 统一营业日、订单和台位状态的数据模型。
2. 建立全局 Token、图标库、导航和基础反馈组件。
3. 重做台位页与订单详情，打通现场主链路。
4. 将创建预订拆为真实两步并增加冲突校验。
5. 重做工作台指标与待办，接入真实数据。
6. 完成角色权限、异常状态、埋点与多端验收。
7. 将会员中心从员工端拆出，作为 P2 顾客端独立迭代。

## 19. 待业务确认项

以下内容不影响 UI 框架启动，但进入接口与高保真设计前必须确认：

- 门店真实营业日起止时间。
- 台位总数、区域、容量、最低消费和真实平面图。
- “确认到店”与“开台”是否必须分开。
- 销售、前台、服务员实际结账权限。
- 预订是否需要订金、留台时限及超时策略。
- 取消、改台、并台和反结账的审批规则。
- 套餐 / 单品真实数据及库存是否需要实时联动。
