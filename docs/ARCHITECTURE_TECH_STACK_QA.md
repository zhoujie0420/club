## 一、架构总览

### Q1：HOLE CLUB 是一个什么类型的系统？

HOLE CLUB 是一套面向夜店单门店经营场景的移动端台位与订单协作系统。

第一阶段以员工运营端为主，服务销售、前台、服务员、店长和老板，覆盖：

- 创建预订
- 实时台位管理
- 客户到店与开台
- 酒水和套餐加单
- 线下收款记录
- 清台与订单完成
- 当日经营数据查看

顾客会员端属于后续独立应用，不与员工端共用导航、登录态和权限模型。

### Q2：推荐采用什么整体架构？

推荐采用“模块化单体后端 + 多端统一前端 + MySQL 主数据库”的架构。

```text
员工 H5 / 微信小程序                 顾客会员端（P2）
          │                                  │
          └──────── HTTPS / JSON API ────────┘
                             │
                     Go API 模块化单体
          ┌──────────┬───────┼────────┬──────────┐
          │          │       │        │          │
        认证权限    台位    订单      商品       经营统计
          │          │       │        │          │
          └──────────┴───────┼────────┴──────────┘
                             │
                    MySQL + Redis（P1）
                             │
                 日志 / 监控 / 对象存储（按需）
```

当前业务规模不需要微服务。模块化单体更容易部署、调试和保持事务一致性，同时保留未来拆分模块的边界。

### Q3：为什么暂时不采用微服务？

因为系统目前是单门店、少角色、低到中等并发，核心难点是订单和台位状态的一致性，不是独立扩容。

过早使用微服务会增加服务发现、分布式事务、链路追踪、部署编排和故障排查成本。当前用一个 Go 服务即可完成清晰分层；等出现多门店、第三方开放平台或某个模块需要独立扩容时，再按模块边界拆分。

### Q4：系统的核心架构原则是什么？

1. **服务端是业务事实来源**：订单、台位、金额和权限不能以 localStorage 为准。
2. **订单与台位强一致**：预订、开台、结账、清台必须在事务中同步状态。
3. **状态流转受控**：客户端不能任意提交目标状态，只能调用明确的业务动作。
4. **写操作可幂等**：弱网重试不能重复创建订单、重复加单或重复结账。
5. **先模块化单体，后按压力拆分**：不为未知规模提前增加复杂度。
6. **员工端与顾客端隔离**：身份、权限、界面和数据暴露范围分别设计。

### Q6：哪些现有技术应该保留？

建议保留：

- UniApp：继续支撑 H5 和微信小程序共用业务代码。
- Vue 3：组件化和 Composition API 适合当前规模。
- TypeScript：约束订单、台位、角色等核心模型。
- Vite：构建速度快，与现有项目兼容。
- Go：适合编写高并发、低资源占用的单体 API。
- MySQL：适合订单、账单和操作日志等强结构化、事务型数据。
- Docker + Railway：适合当前低运维成本的试营业阶段。

不建议在 P0 引入重量级全套 UI 框架。台位图、订单卡和现场操作具有明显业务特征，自建小型组件库更容易保持品牌与交互一致。

### Q9：后端推荐使用什么技术栈？

| 能力 | 推荐技术 | 说明 |
| --- | --- | --- |
| 语言 | Go | 延续现有项目 |
| HTTP 服务 | Go 1.22+ `net/http` | 当前规模足够；路由语法已支持方法和路径 |
| 数据访问 | `sqlc` + `database/sql` | SQL 明确、类型安全、事务边界清晰 |
| 数据迁移 | `golang-migrate` | 数据库结构进入版本控制 |
| 数据库 | MySQL 8 | 订单和台位核心事实库 |
| 缓存 / 锁 | Redis（P1） | 会话、短期缓存、限流；不作为订单事实库 |
| 鉴权 | JWT 短令牌 + 刷新令牌 | 员工登录和 API 鉴权；令牌需可撤销 |
| 参数校验 | 业务层显式校验 | 错误码稳定，不直接返回数据库错误 |
| 日志 | `log/slog` JSON | 带 request_id、user_id、store_id、order_id |
| 指标 | OpenTelemetry / 托管监控 | P1 接入请求、错误率和数据库指标 |
| 错误追踪 | Sentry 或同类服务 | 前后端统一关联 request_id |
| API 文档 | OpenAPI 3 | 作为前后端契约和联调依据 |
| 测试 | Go testing + testcontainers | 单元测试和 MySQL 集成测试 |

P0 可以继续使用标准库路由，不必为“看起来完整”更换 Web 框架。真正需要补齐的是分层、事务、校验、鉴权和测试。

### Q10：数据库为什么选择 MySQL？

订单、台位、支付记录和操作日志之间存在大量关系和事务要求，MySQL 能提供成熟的事务、唯一约束、行锁、索引和备份能力。

项目已经引入 MySQL 驱动并计划部署 Railway MySQL，继续使用可以降低迁移成本。核心业务数据不适合只放在 Redis、文档数据库或客户端缓存中。

### Q11：是否需要 Redis？

MVP 阶段可以不需要。单实例 Go + MySQL 足以支撑早期单门店使用。

以下需求出现时再引入 Redis：

- 多实例部署后的共享会话或令牌撤销列表
- 高频台位状态短缓存
- 接口限流
- 短时分布式锁
- 实时消息广播协调

即使使用 Redis，订单、金额和最终台位状态仍以 MySQL 为准。

## 四、前端架构

### Q12：前端目录应该如何组织？

推荐按“业务模块 + 共享基础能力”组织：

```text
front/src/
├── api/                    # 请求客户端、接口函数、DTO
├── components/
│   ├── base/               # Button、Input、Modal、EmptyState
│   └── business/           # OrderCard、TableSeat、StatusBadge
├── composables/            # 营业日、权限、轮询、表单逻辑
├── constants/              # 枚举、错误码、路由名
├── features/
│   ├── auth/
│   ├── dashboard/
│   ├── tables/
│   ├── bookings/
│   ├── orders/
│   └── checkout/
├── pages/                  # UniApp 页面入口，保持轻量
├── stores/                 # Pinia stores
├── styles/                 # Token、全局样式、主题
├── types/                  # 共享领域类型
└── utils/                  # 金额、日期、脱敏、校验
```

页面只负责编排，不直接包含大量存储、状态流转和请求细节。可复用业务逻辑放入 feature、store 或 composable。

### Q13：前端需要哪些全局 Store？

- `sessionStore`：员工信息、访问令牌、登录状态。
- `storeContextStore`：当前门店、营业日、班次。
- `permissionStore`：角色与细粒度权限。
- `tableStore`：台位配置、实时状态、最后更新时间。
- `orderStore`：当前订单详情、列表筛选和分页状态。
- `appStore`：网络状态、全局提示、版本信息。

不建议把所有接口结果永久塞入一个大 Store。一次性页面数据可保留在页面或 composable 中。

### Q14：前端如何处理 API 请求？

建立唯一请求客户端，统一完成：

1. 拼接 API 基础地址。
2. 添加 `Authorization`、`X-Request-ID`、`X-Store-ID`。
3. 设置连接和业务超时。
4. 将服务端错误码映射为用户可理解的文案。
5. 遇到 401 时刷新令牌或进入登录页。
6. GET 请求可有限重试；写请求只在携带幂等键时重试。
7. 日志中不得打印完整手机号、令牌和支付敏感信息。

### Q15：前端如何实现弱网和离线体验？

- 列表刷新失败时保留最近一次成功数据，并显示更新时间。
- 网络断开时显示常驻提示条。
- 创建订单、加单、结账等写操作离线时禁止提交，避免产生状态冲突。
- 已发出但结果未知的写请求，使用同一个幂等键查询或重试。
- localStorage 仅缓存筛选项、主题偏好和非敏感只读快照，不作为业务真相。

### Q16：实时台位状态如何更新？

分阶段实现：

- P0：页面可见时每 5 秒增量轮询，同时支持手动刷新。
- P1：使用 WebSocket 或 Server-Sent Events 推送台位和订单事件。
- App 进入后台后停止轮询，回到前台立即全量刷新。
- 所有事件带实体版本号；收到旧版本事件时忽略。

单门店初期，轮询更简单可靠，不必一开始就使用 WebSocket。

## 五、后端架构

### Q17：Go 服务应该如何分层？

推荐使用以下职责边界：

```text
HTTP Handler
    ↓ 解析请求、鉴权上下文、返回统一响应
Application Service
    ↓ 编排用例、开启事务、调用领域规则
Domain
    ↓ 状态机、金额、权限和业务不变量
Repository
    ↓ SQL 查询与持久化
MySQL / Redis / 外部服务
```

Handler 不直接写 SQL；Repository 不决定订单是否可以结账；状态流转规则集中在 Domain / Application Service，避免散落在接口中。

### Q18：后端目录应该如何组织？

```text
server/
├── cmd/api/                # 进程入口
├── internal/
│   ├── auth/               # 登录、令牌、权限
│   ├── dashboard/          # 经营概览和待办
│   ├── table/              # 台位配置与状态
│   ├── order/              # 订单、状态机、订单明细
│   ├── catalog/            # 套餐、商品、价格
│   ├── checkout/           # 线下收款记录
│   ├── customer/           # 客户资料（P1）
│   ├── audit/              # 操作日志
│   ├── platform/           # 数据库、日志、配置、HTTP 中间件
│   └── generated/          # sqlc 生成代码
├── migrations/             # MySQL 迁移文件
├── openapi/                # API 契约
└── tests/                  # 集成测试辅助代码
```

业务模块内部可以继续划分 handler、service、repository 和 model，但不需要为每个小文件制造过深目录。

### Q19：API 应该采用 REST 还是 GraphQL？

P0 推荐 REST。当前操作天然是资源读取和明确业务动作，REST 更容易调试、记录、限流和生成文档。

示例：

```text
GET  /api/v1/business-days/current/dashboard
GET  /api/v1/tables
GET  /api/v1/orders
POST /api/v1/orders
GET  /api/v1/orders/{id}
POST /api/v1/orders/{id}/confirm-arrival
POST /api/v1/orders/{id}/open-table
POST /api/v1/orders/{id}/items
POST /api/v1/orders/{id}/checkout
POST /api/v1/orders/{id}/complete-cleaning
POST /api/v1/orders/{id}/cancel
```

订单状态动作使用明确的动作接口，不提供通用的 `PATCH status`，从而让服务端校验每个动作的前置条件和权限。

### Q20：API 返回结构如何统一？

成功响应直接返回资源或列表包装：

```json
{
  "data": [],
  "page": 1,
  "page_size": 20,
  "total": 0
}
```

错误响应使用稳定业务错误码：

```json
{
  "error": {
    "code": "TABLE_ALREADY_OCCUPIED",
    "message": "该台位刚刚被占用，请重新选择",
    "request_id": "req_01...",
    "details": {
      "table_id": "V08"
    }
  }
}
```

HTTP 状态码表达请求类别，业务错误码用于前端选择具体交互。生产环境不得返回 SQL、堆栈或内部路径。

### Q21：如何保证订单和台位状态一致？

关键动作必须在一个数据库事务中完成。

以创建预订为例：

1. 锁定目标台位或查询对应时间段预订冲突。
2. 校验台位启用、容量和可预订状态。
3. 创建订单及订单明细。
4. 写入台位占用关系。
5. 写操作日志。
6. 一次性提交事务。

如果任一步失败，全部回滚。数据库还需通过唯一约束防止同台位、同时间段出现重复有效预订。

### Q22：如何处理并发冲突？

- 每个订单和台位记录包含 `version` 字段，更新时使用乐观锁。
- 关键资源创建和结账使用数据库事务与必要的行锁。
- 写接口接收 `Idempotency-Key`，服务端保存请求结果。
- 冲突返回 HTTP 409 和稳定错误码，前端保留已填写内容并引导刷新。
- 金额由服务端基于商品价格重新计算，不相信客户端总金额。

## 六、核心数据模型

| 表 | 作用 |
| --- | --- |
| `stores` | 门店、营业时间和基础配置 |
| `users` | 员工账号 |
| `roles` / `permissions` | 角色与权限 |
| `user_roles` | 员工角色关联 |

### Q24：订单表最重要的字段有哪些？

建议至少包括：

- `id`：内部主键。
- `order_no`：用户可见订单号，唯一。
- `store_id`、`business_day_id`：门店与营业日。
- `table_id`：当前台位。
- `customer_name`、`customer_phone_encrypted`、`customer_phone_hash`。
- `guest_count`、`arrival_at`、`remark`。
- `sales_user_id`、`created_by`。
- `status`、`version`。
- `subtotal_amount`、`discount_amount`、`receivable_amount`、`paid_amount`。
- `arrived_at`、`opened_at`、`checked_out_at`、`completed_at`、`cancelled_at`。
- `created_at`、`updated_at`。

订单明细必须保存商品名称、单价等成交快照，后续商品改价不能改变历史账单。

### Q25：台位平面图数据应该如何存储？

台位业务数据与展示布局分开：

- 业务字段：台号、区域、容量、最低消费、启停状态。
- 布局字段：`x`、`y`、`width`、`height`、`shape`、`rotation`、`floor`。
- 舞台、舞池、吧台等非台位元素使用独立 `floor_elements` 配置。

前端读取同一个版本化配置生成平面图，统计数量也基于这份配置，不能再分别写死台位数量和台位数组。

### Q26：手机号如何安全存储？

- 数据库中保存加密值，用于有权限时解密展示。
- 额外保存标准化后的不可逆哈希，用于精确查询和去重。
- 日志、埋点、错误追踪中只记录脱敏手机号。
- 查看完整手机号必须通过权限校验并记录审计日志。
- 不在 localStorage、URL 参数或前端错误日志中存储完整手机号。

## 七、认证与权限

### Q27：员工如何登录？

P0 推荐“手机号 / 员工号 + 密码或验证码”登录。登录后服务端返回短期访问令牌和可轮换刷新令牌。

微信小程序可在后续绑定企业员工账号，但微信身份不能直接替代门店权限系统。

### Q28：权限如何设计？

使用 RBAC：用户关联角色，角色关联细粒度权限。例如：

```text
order:create
order:view_all
order:cancel
table:open
order:add_item
payment:checkout
payment:reverse
customer:phone_view
report:revenue_view
```

前端根据权限隐藏或禁用操作，后端必须再次校验。前端隐藏按钮不是安全边界。

### Q29：角色切换如何处理？

现有项目的自由角色切换仅保留在演示环境。生产环境角色由服务端账号权限决定。

如果一个员工拥有多个角色，可以在登录后选择本班次身份，但每次业务操作仍记录真实用户、当前角色、门店和时间。

## 八、部署与环境

### Q30：推荐如何部署？

当前阶段推荐：

```text
GitHub Repository
├── GitHub Actions
│   ├── 前端检查、测试、构建
│   └── 后端检查、测试、镜像构建
├── GitHub Pages / 静态托管：演示 H5
└── Railway
    ├── Go API 容器
    └── MySQL 8
```

正式营业前，员工 H5 应使用带 HTTPS 的独立域名。GitHub Pages 可继续用于演示环境，不建议承载生产员工端。

### Q31：需要哪些环境？

- `local`：开发者本地环境，可使用匿名演示数据。
- `staging`：联调和门店验收，使用独立数据库。
- `production`：真实营业环境，禁止演示账号和自由角色切换。

每个环境使用独立数据库、令牌密钥和 CORS 配置，不允许共用生产凭证。

### Q32：环境变量至少有哪些？

```text
APP_ENV
APP_VERSION
PORT
MYSQL_DSN
CORS_ALLOWED_ORIGINS
JWT_SIGNING_KEY
ACCESS_TOKEN_TTL
REFRESH_TOKEN_TTL
LOG_LEVEL
SENTRY_DSN                  # 可选
REDIS_URL                  # P1 可选
```

敏感值只保存在部署平台 Secret 中，不写入仓库、镜像或前端构建产物。

### Q33：数据库如何备份？

- 生产 MySQL 开启每日自动备份。
- 至少保留 7–30 天，具体由业务合规要求决定。
- 正式营业前完成一次恢复演练，确认备份确实可用。
- 数据迁移先在 staging 验证；涉及删除或改列的迁移采用兼容式分阶段发布。

## 九、测试与质量保障

### Q34：测试应该覆盖哪些层级？

| 层级 | 重点 |
| --- | --- |
| 前端单元测试 | 金额、营业日、权限判断、状态文案、表单规则 |
| 前端组件测试 | 订台表单、订单操作栏、确认弹窗 |
| 后端单元测试 | 订单状态机、权限、金额、不变量 |
| 后端集成测试 | MySQL 事务、唯一约束、并发和幂等 |
| API 契约测试 | OpenAPI 与真实返回结构一致 |
| E2E | 创建预订 → 到店 → 开台 → 加单 → 结账 → 清台 |
| 人工验收 | 弱网、跨日、键盘、安全区、不同角色 |

### Q35：哪些流程必须作为发布阻断测试？

- 同一台位同一时段不能重复预订。
- 重复点击创建订单只能产生一笔订单。
- 无权限角色无法结账或查看完整手机号。
- 加单后订单总额计算正确。
- 结账失败时订单不能进入待清台。
- 完成清台后台位恢复空闲。
- 跨凌晨后订单仍归属正确营业日。
- 列表、详情、工作台金额和状态一致。

### Q36：CI/CD 流程应该是什么？

每次 Pull Request 执行：

1. 前端依赖安装、类型检查、单元测试和构建。
2. Go 格式、静态检查、单元测试和集成测试。
3. 数据库迁移校验。
4. OpenAPI 契约检查。
5. 主链路 E2E 测试。

合并主分支后自动部署 staging；production 由人工确认发布。数据库迁移在应用发布前执行，并确保新旧版本短期兼容。

## 十、监控与运维

### Q37：生产环境要监控什么？

- API 可用率、P50 / P95 / P99 延迟。
- HTTP 4xx / 5xx 和业务错误码分布。
- MySQL 连接数、慢查询、锁等待和存储空间。
- 创建订单、加单、结账的成功率。
- 台位状态更新时间和前端数据陈旧时间。
- 重复请求、幂等命中和并发冲突次数。
- 前端 JavaScript 错误和白屏率。

### Q38：日志需要记录什么？

每条请求日志至少包含：

- `timestamp`
- `level`
- `request_id`
- `method`、`path`、`status`、`duration_ms`
- `store_id`、`user_id`
- 必要时包含 `order_id`、`table_id`

严禁记录令牌、密码、完整手机号、数据库 DSN 和其他敏感信息。

### Q39：服务健康检查如何设计？

- `/healthz`：只表示进程存活，不依赖数据库。
- `/readyz`：表示是否可以接收业务流量，应检查数据库连接。
- 部署平台用 readiness 决定是否转发请求。
- 监控平台额外执行一条只读核心 API 合成检查，验证真实业务链路。

当前项目已经有 `/healthz` 和 `/readyz`，可以直接延续并补充监控。

## 十一、性能与容量

### Q40：单门店需要多高的并发能力？

早期按以下目标设计即可：

- 50–100 名员工账号。
- 营业高峰 20–50 个同时在线客户端。
- 台位状态查询峰值 20–50 QPS。
- 写操作峰值 5–10 QPS。
- API P95 读取延迟低于 300 ms，写入低于 500 ms。

一个合理配置的 Go 实例和 MySQL 足够支撑。应先通过索引、分页、连接池和查询优化解决问题，再考虑拆服务。

### Q41：数据库索引重点是什么？

- `orders(store_id, business_day_id, status, arrival_at)`
- `orders(store_id, table_id, status)`
- `orders(order_no)` 唯一索引
- `orders(customer_phone_hash)`
- `order_items(order_id)`
- `payments(order_id, status)`
- `order_events(order_id, created_at)`
- 台位有效占用的唯一约束或等价冲突控制结构

索引需要以真实查询和 `EXPLAIN` 结果调整，不能只按字段数量堆叠。

## 十二、演进路线

### Q42：从当前代码到正式版本，推荐如何分阶段？

#### 阶段 1：工程基础

- 重组前后端目录。
- 建立 Design Token、基础组件和 Pinia。
- 建立数据库迁移、OpenAPI、统一错误码和日志。
- 创建门店、用户、角色、台位、订单核心表。

#### 阶段 2：核心闭环

- API 接管 localStorage 演示订单。
- 打通创建预订、到店、开台、加单、结账、清台。
- 加入事务、权限、幂等和操作日志。
- 完成核心 E2E 测试。

#### 阶段 3：现场稳定性

- 台位增量轮询、冲突处理、弱网体验。
- 接入错误追踪、监控、自动备份。
- 完成门店数据配置和真实设备验收。

#### 阶段 4：经营增强

- 客户档案、销售排行、异常订单、改台 / 并台。
- Redis、实时推送按实际压力引入。

#### 阶段 5：顾客会员端

- 独立顾客身份体系。
- 自助订台、订金支付、会员、积分与权益。

### Q43：未来什么时候应该拆微服务？

出现以下一个或多个信号时再评估：

- 多门店数量增长，单体发布频率和团队协作互相阻塞。
- 支付、会员或消息模块需要独立合规、扩容或故障隔离。
- 某模块负载显著高于其他模块，且数据库边界可以独立。
- 已具备成熟 CI/CD、可观测性和运维能力。

优先可能拆出的模块是消息通知、会员营销、报表分析和支付接入；订单与台位在业务早期应尽量保持在同一事务边界内。

## 十三、关键技术决策结论

### Q44：这套方案最终推荐的技术栈是什么？

**前端**：UniApp + Vue 3 + TypeScript + Vite + Pinia + SCSS Design Token + Day.js + Vitest + Playwright。

**后端**：Go 1.22+ + `net/http` + `database/sql` + sqlc + golang-migrate + OpenAPI 3 + `log/slog`。

**数据**：MySQL 8 为主数据库；Redis 在 P1 按实际需求引入。

**部署**：GitHub Actions + Docker + Railway；演示 H5 可保留 GitHub Pages，生产使用独立 HTTPS 域名。

**监控**：结构化日志 + request_id + 错误追踪；P1 接入 OpenTelemetry 或托管指标平台。

### Q45：最先应该做的三件事是什么？

1. 建立 MySQL 数据模型、迁移和订单 / 台位事务规则，替换 localStorage 业务真相。
2. 建立认证权限、统一 API 契约和幂等写入机制。
3. 以前端 Design Token 和模块化目录重构主链路，完成端到端自动化测试。

这三项完成后，项目才从“可交互演示”进入“可安全联调和试营业”的阶段。
